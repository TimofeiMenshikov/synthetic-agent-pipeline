# Синтетические агентские задачи и SFT-траектории

Рабочий локальный MVP: генерирует задачи на CSV и SQLite, запускает учителя через ограниченные инструменты, проверяет результат по отдельному эталону и экспортирует только принятые траектории. Нужен Python 3.10 или новее. Сторонние зависимости для запуска и тестов не требуются.

Это независимая реализация подходов NexGAP для трёх фиксированных семейств задач. Формулировки и данные создаются детерминированными шаблонами; полный пайплайн NexForge здесь не воспроизводится.

После клонирования все команды выполняются из корня репозитория.

Результаты выполненных прогонов и проверок: [REPORT.md](REPORT.md).

## Быстрый локальный прогон

```sh
git clone https://github.com/TimofeiMenshikov/synthetic-agent-pipeline.git
cd synthetic-agent-pipeline

python3 -m synthetic_agent_pipeline run \
  --mode mock --count 20 --seed 20261117 \
  --mock-fail-every 5 --run-id nex20-reject \
  --output artifacts --max-steps 16 --timeout 30
```

Mock решает задачи по ответам инструментов, без API и доступа к эталонам. `--mock-fail-every 5` намеренно искажает каждый пятый результат, чтобы проверить отбраковку неверных решений. Это диагностический режим: его результаты находятся в `artifacts/mock/nex20-reject/`, включая JSONL для проверки формата. Эти записи нельзя использовать для SFT: mock воспроизводит заданный алгоритм, а не поведение модели-учителя.

Проверенный результат этой команды: 20 задач сгенерировано, 16 принято, 4 отбраковано; в train попало 11 траекторий, в validation — 5. Без намеренных ошибок mock принимает все 20 задач.

Числа сгенерированных, принятых и отбракованных задач, причины отказов и размеры выборок сохраняются в `report.json`. Подробности по каждой задаче находятся в `results.jsonl`; отклонённые задачи дополнительно записаны в `rejected.jsonl`. Для повторного запуска используй новый `--run-id`.

Проверить экспортированные JSONL:

```sh
python3 -m synthetic_agent_pipeline check-jsonl artifacts/mock/nex20-reject/exports/train.jsonl
python3 -m synthetic_agent_pipeline check-jsonl artifacts/mock/nex20-reject/exports/validation.jsonl
```

## Запуск реальной модели-учителя

Задай ключ и имя доступной тебе модели с поддержкой function calling. Например, после безопасной загрузки ключа в `TEACHER_API_KEY`:

```sh
export TEACHER_BASE_URL='https://api.openai.com/v1'
export TEACHER_MODEL='имя-доступной-модели'
python3 -m synthetic_agent_pipeline run \
  --mode teacher --count 20 --seed 20261117 \
  --timeout 120 --max-steps 16 --run-id teacher20 --output artifacts
```

Адаптер отправляет `POST <TEACHER_BASE_URL>/chat/completions` с `messages`, `tools` и `tool_choice=auto`. Для другого OpenAI-совместимого сервера укажи его базовый URL вместе с API-префиксом, например `/v1`; суффикс `/chat/completions` добавляется автоматически. Ключ обязателен и для локального сервера — если он не проверяет авторизацию, используй согласованное с его настройками непустое значение.

| Настройка | Переменная | Алиас |
| --- | --- | --- |
| API-ключ | `TEACHER_API_KEY` | `OPENAI_API_KEY` |
| Базовый URL | `TEACHER_BASE_URL` | `OPENAI_BASE_URL`, `OPENAI_API_BASE` |
| Имя модели | `TEACHER_MODEL` | `OPENAI_MODEL` |

Переменные `TEACHER_*` имеют приоритет. URL по умолчанию — `https://api.openai.com/v1`; имя модели нужно задать явно. Ключ не записывается в артефакты. Реальные траектории сохраняются отдельно, в `artifacts/teacher/teacher20/`. При отсутствии ключа конфигурация teacher отклоняется до вызова API. При разработке этой версии ключа не было, реальных запросов к модели не выполняли.

`--timeout` задаёт общий тайм-аут одной задачи в секундах. Каждая задача выполняется в отдельном процессе и рабочем каталоге; родительский процесс принудительно останавливает её по истечении срока. `--max-steps` ограничивает количество ходов учителя и включает последний текстовый ответ после записи результата. На одном ходу разрешено не более 8 вызовов инструментов. Ошибки API, незавершённые диалоги и превышение лимитов сохраняются как причины отбраковки.

## Семейства задач

| Семейство | Данные и действия | Результат |
| --- | --- | --- |
| `table_reconciliation` | Прочитать счета и платежи из двух CSV; сопоставить объединение идентификаторов | Отсутствующие платежи, лишние платежи и несовпадающие суммы |
| `inventory_discrepancies` | Прочитать складской снимок CSV; изучить SQLite; вычислить начальные остатки плюс движения | Ненулевые расхождения между расчётными и зафиксированными остатками |
| `sales_summary` | Прочитать заказы CSV; изучить SQLite; получить регионы клиентов SQL-запросом | Число оплаченных заказов и выручка по всем регионам, включая нулевые |

Генератор чередует семейства и уровни `easy`, `medium`, `hard`; сложность меняет объём данных и число расхождений. Каждая задача содержит стабильные `task_id`, `family`, `difficulty`, исходный `seed` и отдельный `task_seed`. Промпт задаёт точную структуру результата и порядок строк. Денежные суммы представлены целыми копейками.

Эталоны вычисляются непосредственно из записей генератора на Python. Они лежат в `generated/references/`, за пределами публичных данных и рабочего каталога агента. Учитель видит формулировку и копию публичных входных файлов. Одинаковые `seed` и `count` дают одинаковые задания; тест проверяет побайтное совпадение, включая SQLite, на одной версии SQLite.

По умолчанию всё семейство `sales_summary` уходит в validation; остальные семейства — в train. Разделение происходит по семействам, поэтому разные варианты одного семейства не оказываются в обеих выборках. `task_id`, seed, семейство и сложность сохраняются в сопроводительном `exports/index.jsonl`, а обучающие строки следуют изученному образцу: `messages`, `tools`, `uuid`, `generator`.

## Инструменты и проверка

Модели доступны `list_files`, `read_csv`, `inspect_database`, `query_sql`, `write_result`. Чтение ограничено файлами внутри `data/`; запись — единственным `output/result.json`. Абсолютные пути, выход через `..` и символические ссылки запрещены. SQL-соединение открывается только для чтения; проверяются тип запроса, разрешённые действия SQLite, объём результата и время выполнения. Shell, Python и произвольного доступа к файловой системе у модели нет.

Это ограничения набора инструментов, а не системная песочница для запуска недоверенного локального кода: рабочие каталоги должен контролировать владелец процесса. MVP рассчитан на сгенерированные небольшие CSV и SQLite, без параллельной подмены файлов сторонними процессами.

Проверка сравнивает JSON результата с эталоном строго: поля, типы, значения, количество и порядок строк. Лишние поля, пропущенные или повторённые строки, дробные числа вместо целых, `true` вместо `1`, повторённые JSON-ключи и `NaN` отклоняются. Отдельно проверяется траектория: каждому ответу инструмента соответствует предыдущий вызов через `tool_call_id`; идентификаторы не повторяются, незавершённых вызовов нет. Для принятой траектории нужны несколько чтений данных, запись результата и завершающий ответ учителя. Траектории с ошибками инструментов исключаются из экспорта, даже если итоговый файл оказался верным.

## Артефакты

```text
artifacts/
  mock/<run-id>/                 # диагностические записи mock
  teacher/<run-id>/              # реальные траектории учителя
    generated/
      manifest.jsonl
      queries.jsonl             # поля QueryExporter Gyrfalcon
      tasks/<task-id>/public/
        task.json
        data/
      references/<task-id>.json
    workspaces/<task-id>/
      task.json
      data/
      output/result.json
    traces/<task-id>/
      events.jsonl
      generation_spans.jsonl    # input/output каждого хода учителя
      messages.json
      status.json
    results.jsonl
    rejected.jsonl
    exports/
      train.jsonl
      validation.jsonl
      index.jsonl
    report.json
    source_audit.json
    reference_compatibility.json
```

Каждая строка обучающего JSONL — объект с `messages`, `tools`, `uuid` и `generator`, как в изученной выборке `tool_calling.jsonl`. У каждого сообщения есть массив `tool_calls`; без вызовов он пуст. `content` всегда строка, в том числе пустая. Аргументы функции сериализованы JSON-строкой; ответы имеют `role: "tool"` и `tool_call_id`. UUID детерминирован по task_id; `generator` отличает mock от teacher. Нативные сообщения API сохраняются отдельно без этих преобразований.

По подходу NexGAP сохраняется input/output каждого хода учителя. Конвертер выбирает последний generation и собирает его полную историю с финальным ответом; префиксы не повторяются. Перед экспортом проверяются согласованность snapshots и совпадение с рабочей трассой. `exports/index.jsonl` связывает запись с task_id, trace_id и span_id. Полные вызовы и ответы сохраняются и для отклонённых задач.

## Отдельная генерация и тесты

Сгенерировать входные данные без запуска учителя:

```sh
python3 -m synthetic_agent_pipeline generate \
  --output /tmp/synthetic-tasks --count 20 --seed 20261117
```

Папка назначения должна быть пустой: генератор отказывается смешивать новые задания с предыдущей партией.

```sh
python3 -m unittest discover -s tests -v
```

Тесты проверяют воспроизводимость seed, положительные и отрицательные результаты детерминированного судьи, ограничения инструментов, формат ответов совместимого API и связи вызовов в траекториях. Mock-прогон нужен дополнительно, чтобы проверить весь путь от файлов задания до экспортированных JSONL.

В зафиксированной проверке прошли все 52 теста при наличии внешнего архива. Без архива тест потокового чтения исходного `tool_calling.jsonl` автоматически пропускается; остальные тесты и оба режима пайплайна от него не зависят.

## Источники и необязательный архив NexGAP

Архив NexGAP и датасеты — необязательные внешние материалы. Они не входят в репозиторий и не нужны для генерации, mock или запуска учителя. Локальные результаты в `artifacts/` также исключены из Git. Изученные исходники сохранены без изменений; проверка выбранных файлов записана в [archive-preservation.json](archive-preservation.json).

Прочитаны `Gyrfalcon/core/pipeline.py`, примеры frameworks и `QueryExporter`, `run_end_to_end.py`, преобразователи в `converter/trace/`. Потоково изучены первые 5 записей каждого `tool_calling.jsonl` и `agent.jsonl`; большие датасеты не загружаются целиком. Структура выборки без текста исходных задач записана в [reference-format.json](reference-format.json). Карта использованных идей и ссылок — [SOURCE_NOTES.md](SOURCE_NOTES.md).

Конфигурация `synthetic_agent_pipeline/configs/local_csv_sqlite.json` задаёт framework, persona, дерево типов, расписание и параметры сложности. Отдельный `generated/queries.jsonl` использует поля экспорта Gyrfalcon. В MVP формулировки и данные генерируются детерминированными шаблонами; LLM используется как учитель при решении. Динамическое расширение дерева и Langfuse не нужны для локального домена.

```sh
NEX_ARCHIVE=../nex-archive-2026-11-17
python3 -m synthetic_agent_pipeline audit-sources --archive "$NEX_ARCHIVE"
python3 -m synthetic_agent_pipeline check-reference \
  artifacts/mock/nex20-reject/exports/train.jsonl --archive "$NEX_ARCHIVE"
```

Для явного пути к внешнему архиву добавь `--archive "$NEX_ARCHIVE"` к команде `run`. По умолчанию проверяется соседняя папка `../nex-archive-2026-11-17/`; там же необязательный тест ищет исходный датасет.

При доступном архиве прогон автоматически сравнивает экспорт с соглашениями сериализации двух потоково прочитанных записей локального `tool_calling.jsonl` и сохраняет `reference_compatibility.json`. Это проверка формата выборки, а не утверждение о всём датасете или качестве реального учителя. `agent.jsonl` содержит обычные диалоги; для этого MVP выбран структурированный формат `tool_calling.jsonl`.

В MVP нет восстановления прерванного прогона и автоматических повторов API-запросов. Принятие решения определяет детерминированная проверка. Для реальной SFT-партии нужно измерить долю успешных решений выбранной модели и подтвердить настройки конкретного тренера.
